- **Let `docker/` sandbox support concurrent use across worktrees/agents on one machine.** Added 2026-09-13. Right now only one worktree/agent can build or run it at a time: `docker-compose.yml` pins a fixed Compose project name (`opencode-qwen-prompt`) and a fixed `container_name` (`opencode-qwen-prompt-dev`) on purpose, so its named volumes (`opencode-config`, `opencode-data`) persist regardless of which worktree invokes it — but that also means two concurrent `docker compose run`/`up` calls from different worktrees collide on that same container name. Worse than a flaky retry: the bind-mounted repo path (`..`, relative to wherever `docker-compose.yml` is invoked from) differs per worktree, so whichever container wins the name race decides which worktree's files actually end up mounted inside it. See `docker/docker-notes.md` and the matching `CLAUDE.md` Hard-won-lessons entry for how this was confirmed (by reading the compose file, not by reproducing the race live). Needs an actual fix — e.g. deriving the project/container name from the worktree path so each gets its own, or some other isolation mechanism — before running multiple agents against this repo at once on one machine is safe. Whatever the fix, it has to preserve the reason the name is pinned today: shared named-volume state (`opencode.jsonc`, logs) surviving across worktrees on purpose — so this isn't just "stop pinning the name," it needs a design that keeps that if still wanted, or a deliberate decision to drop it.
