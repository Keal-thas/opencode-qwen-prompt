- **Let `docker/` sandbox support concurrent use across worktrees/agents on one machine.** Added 2026-09-13. Right now only one worktree/agent can build or run it at a time: `docker-compose.yml` pins a fixed Compose project name (`opencode-qwen-prompt`) and a fixed `container_name` (`opencode-qwen-prompt-dev`) on purpose, so its named volumes (`opencode-config`, `opencode-data`) persist regardless of which worktree invokes it — but that also means two concurrent `docker compose run`/`up` calls from different worktrees collide on that same container name. Worse than a flaky retry: the bind-mounted repo path (`..`, relative to wherever `docker-compose.yml` is invoked from) differs per worktree, so whichever container wins the name race decides which worktree's files actually end up mounted inside it. See `docker/docker-notes.md` and the matching `CLAUDE.md` Hard-won-lessons entry for how this was confirmed (by reading the compose file, not by reproducing the race live). Needs an actual fix — e.g. deriving the project/container name from the worktree path so each gets its own, or some other isolation mechanism — before running multiple agents against this repo at once on one machine is safe. Whatever the fix, it has to preserve the reason the name is pinned today: shared named-volume state (`opencode.jsonc`, logs) surviving across worktrees on purpose — so this isn't just "stop pinning the name," it needs a design that keeps that if still wanted, or a deliberate decision to drop it.
  **Decided direction (Franco, 2026-09-14):** isolate per worktree, not globally. Each worktree should be able to run its own `docker compose` independently and concurrently with other worktrees — derive the project/container name from the worktree path (e.g. a hash or sanitized path suffix) so two worktrees never collide. Within a single worktree, do NOT add locking/serialization for multiple concurrent `docker compose run` invocations — if someone runs two at once in the same worktree, that's on them to manage, not something the tooling needs to guard against. This means the fix only needs to solve cross-worktree collisions, not same-worktree concurrency.

  Design worked out 2026-09-13/14, closing the named-volume-sharing tradeoff the decision above leaves open: hash the worktree's absolute path into `COMPOSE_PROJECT_NAME` (stable per worktree, not random — avoids leaking a new default network per invocation); drop both `container_name:` overrides entirely and let Compose auto-derive names (verified live: 20 concurrent `docker compose run --rm` in the same project never collided on container name, confirming same-worktree concurrency is safe with no added locking, matching the decision above; the shared per-project default network does race on creation but Compose swallows the "already exists" error and every run still exited 0 — benign); drop the `opencode-config`/`opencode-data` named volumes entirely rather than trying to keep them shared (verified: with no plugin configured, not persisting them costs ~0 — cold ~0.49s vs warm ~0.35-0.4s; with a plugin configured it's a real ~20-24s cold penalty because opencode installs the plugin's dependency tree into `~/.config/opencode/node_modules` from scratch every time — verified reproducible 3x); eliminate that 20s cost by pre-installing the plugin's `node_modules` at Docker image build time instead (verified: a container `commit`ted after that install starts warm, ~0.6s, with no volume needed — the image is global/shared across worktrees already, so this cost is paid once per image build, not per worktree/container); keep `oracle` genuinely shared by splitting it into its own `docker/docker-compose.oracle.yml` with a fixed project name, with `opencode-dev`'s (now worktree-hashed) compose project joining it over an `external: true` Docker network instead of `depends_on` in the same file. Full writeup with the reasoning and measurements behind each piece: see git history / ask for the `.local/docker-sandbox-concurrency-design-2026-09-13.md` writeup from the session that produced this (that file itself is gitignored scratch, not committed).

  Two residual risks in that design, deliberately deferred rather than solved (both are separate from the container-name collision that's the point of this TODO, and small enough not to block implementing the rest): see the two new TODO items below.

- **Oracle singleton first-time-startup race (deferred).** Added 2026-09-13, arises from the docker-sandbox-concurrency design above (not yet implemented). Splitting `oracle` into its own fixed-name compose project keeps it genuinely shared (worth it for the 1-3 min warm-DB benefit), but `container_name` there is still fixed on purpose (it's meant to be a singleton) — verified live: if two worktrees both race to bring up that container for the very first time ever on a machine (nobody has started Oracle yet), one `docker compose up -d` succeeds and the other gets a real, non-zero-exit `Conflict: container name already in use` error, unlike the benign default-network race. Once Oracle is already running, later concurrent `up -d` calls from any worktree are fine (idempotent reconcile against the existing container). Narrow window, low blast radius (just retry), not worth solving now — a `flock`-style lock around "ensure Oracle is up" in the wrapper script would close it if it ever actually bites.

- **Docker image tag (`opencode-qwen-prompt-dev:latest`) build race across worktrees (deferred).** Added 2026-09-13, arises from the docker-sandbox-concurrency design above. The image itself is deliberately global/shared across all worktrees (rebuilding a multi-GB toolchain image per worktree would be wasteful, and the toolchain doesn't depend on worktree identity) — so it sits outside the worktree-hash project-name isolation entirely, on purpose. If two worktrees have different uncommitted `Dockerfile` content (e.g. one is mid-edit on the sandbox redesign itself) and both run `docker compose build` around the same time, whichever finishes last silently wins the `:latest` tag — the other's successful build just becomes untagged/dangling, and that worktree's next `docker compose run` quietly uses someone else's image instead of the one it just built, with no error. Not solved here — same "small, deferred" treatment as the Oracle race above.
