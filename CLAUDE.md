# Working notes for this repo

See README.md for what the project does and its current status/open items, and TODO.md for concrete follow-up work still to be done. This file is about *how* to work on it.

## Preferences

Single-person project used across multiple machines/environments (this Mac, the Windows target machine, wherever it's cloned next) — these preferences are git-tracked here, instead of living only in a Claude Code memory file tied to one machine/account, specifically so they hold regardless of which environment a session is running in.

- **Deliver anything needing confirmation or unhurried reading as a file, not a chat wall of text.** Keep the chat reply itself to one or two sentences: the headline plus a pointer to the file. Attention is limited and chat output doesn't get read exhaustively. This repo uses a gitignored `.local/` directory at the repo root for exactly this (scratch notes, session summaries, pending-decision write-ups); clean up a `.local/` file once its content has actually been acted on, don't let it accumulate.
- **Verify claims against the real system when the tooling exists, rather than reasoning from inspection alone.** Has caught real bugs: a `.json`/`.jsonc` false alarm, `module-analysis`'s silent `explore`→`build` fallback, a `docker-compose.yml` relocation that silently changed the Compose project name. Applies on any machine, not just where these specific incidents happened. See [lessons-learned.md](docs/lessons-learned.md) for the full incidents and more.
- **Centralize a config value in one place instead of repeating the literal across files.** E.g. don't let the same Docker image version drift by being hardcoded independently in `Dockerfile`'s `ARG` and in prose docs — the concern is drift risk, not tidiness. Historical/dated facts ("verified against version X on date Y") are exempt; this is about *live* config values.
- **Don't manually wrap prose lines when writing documents.** The editor in use (IntelliJ) has soft-wrap on; write each paragraph as one long source line. Applies to markdown/prose — code comments still wrap per normal language convention. Don't proactively reflow an old file for this; only fix it while otherwise editing that file.
- **All development and testing happens inside the `docker/` sandbox, never directly against the host's own node/opencode/npm install.** Run `./tests/run-all.sh` to build the sandbox image and run the whole suite; iterate faster with `docker/dev.sh run --rm opencode-dev bash tests/run-in-container.sh`. Always go through `docker/dev.sh`, not `docker compose` directly — it isolates this worktree's Compose project so concurrent worktrees never collide (see `docker/docker-notes.md`). Exception: `tests/integration/docker-prompt-override.test.sh` runs on the host because it's what invokes `docker run` in the first place — but everything it actually asserts on still executes inside a disposable container.

- **Two separate machines, don't conflate them.** (1) The restricted/offline machine: single-user, Windows, git-bash, no public internet — where SETUP.md actually gets executed (also used via `web`/`serve` modes, not just CLI — all interfaces read the same `opencode.json`). opencode itself is already installed there via `npm install -g opencode-ai`. **Confirmed 2026-09-17 (Franco, high confidence): this machine does have a working internal npm registry reachable over the intranet, for downloading only — it cannot be used to publish/release this repo's own code.** "No internet" only ever meant no public/external access, not no registry at all. This is why `mcp/oracle/`/`mcp/loki/`'s third-party npm dependencies (`@modelcontextprotocol/sdk`, `oracledb`) install directly via `npm install` now (SETUP.md steps 6/7, see `mcp/TODO.md`) — that registry is a full mirror of public npm, not a curated subset — but it does *not* help `plugins/`'s own plugin code get resolved by package name against this registry (nothing to install from, since it was never published) — those still ship as committed, pre-packed tarballs extracted by hand into opencode's own package cache (see the table entry below). (2) A *separate* vLLM model-serving machine reachable over the restricted machine's internal network — Franco has no admin access to it, only consumes it as an API client; no multi-user file-contention concern on the opencode side.
  Model in use: **`Qwen3.6-35B-A3B`** (real, released 2026-04-16, Apache 2.0, sparse MoE — postdates the knowledge cutoff, don't rely on training-data recall). Native context 262,144 tokens, extensible to 1,010,000 via RoPE scaling. Has a "thinking preservation" feature (retains reasoning traces across multi-turn) — worth checking whether `opencode.json`'s model config sets `reasoning`/`interleaved` to use it. Hardware specs of the model server unknown. `$CONFIG_DIR` on the restricted machine is opencode's default (no override).

- **Whole-repo npm publish, added 2026-09-18 (Franco's call).** The root `package.json` packages the entire git-tracked tree as `@kealthas-dev/opencode-qwen-prompt` on public npmjs.com — not a real dependency for anything, purely a second download channel alongside the existing `v*`-tag GitHub Release zip (`.github/workflows/release.yml`), so the restricted machine's internal npm mirror (download-only, see above) can `npm pack @kealthas-dev/opencode-qwen-prompt@<version>` directly instead of a manual zip transfer — `npm pack`, like `npm install -g`, needs no local host project, it just fetches and writes the tarball as-is. `license: "UNLICENSED"` because public/downloadable here is a means to an end, not an invitation for outside use. Two things had to be fixed to get the right file set published, found via `npm publish --dry-run` before the first real publish rather than by inspection: (1) publishing straight from the working directory risks sweeping in untracked files (a real, non-`.env.example` credentials file someone happens to have sitting in `mcp/*/`, scratch output, etc.) regardless of `.gitignore` — `scripts/publish-npm.sh` avoids this by exporting the current `HEAD` with `git archive` into a clean temp dir first, and publishing only from there; (2) even from that clean export, npm's own packing step *separately* falls back to reading `.gitignore` as its exclusion list whenever there's no `.npmignore` — which would silently drop `docs/opencode-docs-reference/` and `deploy/models-dev-snapshot.json` (both intentionally gitignored-but-tracked, see above, and both things the offline machine actually needs) even though `git archive` had included them correctly. Fixed by committing an intentionally-empty root `.npmignore` — its mere presence stops the gitignore-fallback. First real publish succeeded 2026-09-18 (`1.0.0`, manual `npm login` + interactive 2FA approval in a browser, not a classic TOTP code — Franco's npm account isn't set up with an authenticator app). Ongoing releases are automated via npm **Trusted Publishing** (OIDC, GA since mid-2025) instead of a stored automation token: `release.yml`'s `v*`-tag job now also publishes to npm, using `npm pkg set version="${GITHUB_REF_NAME#v}"` to derive the published version from the tag rather than hand-syncing `package.json`. Requires a matching Trusted Publisher entry on the npm package's Settings page (org `Keal-thas`, repo `opencode-qwen-prompt`, workflow filename `release.yml`, direct `npm publish` explicitly allowed — new configs default to stage-only as of a 2026-09-03 npm change) — configured 2026-09-18. `scripts/publish-npm.sh` still exists for ad-hoc manual publishes between tags. First live CI run (`v1.0.1`, 2026-09-18) caught a real bug that dry-run/inspection had missed: unlike `scripts/publish-npm.sh`, the CI job runs `npm publish` directly against the `actions/checkout` tree rather than a `git archive`'d clean copy — and the "Build zip with .git included" step (writing `<repo>-<tag>-with-git.zip` into that same working directory for the GitHub Release asset) used to run *before* the npm publish step, so that freshly-built zip got swept straight into the published npm tarball too (117 files instead of 116, `1.0.1` shipped with a stray ~2.5MB zip-of-the-repo inside it — harmless for this package's actual purpose, but wrong, and permanent: npm won't let a published version be reused even after unpublishing). Fixed by reordering the job so "Publish to npm" runs before "Build zip with .git included" — the working tree is clean at publish time again. **Not yet re-verified after the reorder fix** (next real tag push will be the first real test of the corrected order) — see this file's "verify against the real system" preference above. Separately, a real `npm pack` pull through the restricted machine's internal mirror still hasn't been confirmed (see TODO.md / `.local/human-todo-verify-npm-pack.md`).
