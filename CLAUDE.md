# Working notes for this repo

See README.md for what the project does and its current status/open items, and TODO.md for concrete follow-up work still to be done. This file is about *how* to work on it.

## Preferences

Single-person project used across multiple machines/environments (this Mac, the Windows target machine, wherever it's cloned next) — these preferences are git-tracked here, instead of living only in a Claude Code memory file tied to one machine/account, specifically so they hold regardless of which environment a session is running in.

- **Deliver anything needing confirmation or unhurried reading as a file, not a chat wall of text.** Keep the chat reply itself to one or two sentences: the headline plus a pointer to the file. Attention is limited and chat output doesn't get read exhaustively. This repo uses a gitignored `.local/` directory at the repo root for exactly this (scratch notes, session summaries, pending-decision write-ups); clean up a `.local/` file once its content has actually been acted on, don't let it accumulate.
- **Verify claims against the real system when the tooling exists, rather than reasoning from inspection alone.** Has caught real bugs: a `.json`/`.jsonc` false alarm, `module-analysis`'s silent `explore`→`build` fallback, a `docker-compose.yml` relocation that silently changed the Compose project name. Applies on any machine, not just where these specific incidents happened. See [lessons-learned.md](docs/lessons-learned.md) for the full incidents and more.
- **Centralize a config value in one place instead of repeating the literal across files.** E.g. don't let the same Docker image version drift by being hardcoded independently in `Dockerfile`'s `ARG` and in prose docs — the concern is drift risk, not tidiness. Historical/dated facts ("verified against version X on date Y") are exempt; this is about *live* config values.
- **Don't manually wrap prose lines when writing documents.** The editor in use (IntelliJ) has soft-wrap on; write each paragraph as one long source line. Applies to markdown/prose — code comments still wrap per normal language convention. Don't proactively reflow an old file for this; only fix it while otherwise editing that file.
- **All development and testing happens inside the `docker/` sandbox, never directly against the host's own node/opencode/npm install.** Run `./tests/run-all.sh` to build the sandbox image and run the whole suite; iterate faster with `docker/dev.sh run --rm opencode-dev bash tests/run-in-container.sh`. Always go through `docker/dev.sh`, not `docker compose` directly — it isolates this worktree's Compose project so concurrent worktrees never collide (see `docker/docker-notes.md`). Exception: `tests/integration/docker-prompt-override.test.sh` runs on the host because it's what invokes `docker run` in the first place — but everything it actually asserts on still executes inside a disposable container.

`docs/opencode-docs-reference/` is a git-tracked, committed mirror of all 36 top-level English `.mdx` pages from upstream `packages/web/src/content/docs/` (locale subdirs skipped) — the target machine has no internet, so this travels with the repo. Refresh with `./docs/fetch-opencode-docs.sh`. It's *also* listed in `.gitignore` on purpose (doesn't untrack it — see [lessons-learned.md](docs/lessons-learned.md) for the ripgrep-vs-git behavior this relies on); the one cost is a brand-new file under it needs `git add -f`.

- **opencode upstream**: [anomalyco/opencode](https://github.com/anomalyco/opencode) (`dev` branch), npm package `opencode-ai`. Agent definitions: `packages/opencode/src/agent/agent.ts`. `explore`/`compaction`/`summary`/`title` each load their own native prompt from `packages/opencode/src/agent/prompt/*.txt`; `build`, `plan`, and `general` have **no prompt field set in source at all** (confirmed against 1.14.30, re-confirmed 2026-09-13 against 1.18.30 — re-check this on future upgrades rather than assuming it still holds). Permission logic: `packages/opencode/src/permission/index.ts`. Task tool (subagent invocation): `packages/opencode/src/tool/task.ts` + `task.txt`. Base-prompt-by-model-ID selection: `packages/opencode/src/session/system.ts`.
- The target machine's model server (vLLM) exposes an **OpenAI-compatible API** — relevant for the `provider` block in `opencode.json`; opencode supports OpenAI-compatible providers natively.
- **Two separate machines, don't conflate them.** (1) The restricted/offline machine: single-user, Windows, git-bash, no internet — where SETUP.md actually gets executed (also used via `web`/`serve` modes, not just CLI — all interfaces read the same `opencode.json`). (2) A *separate* vLLM model-serving machine reachable over the restricted machine's internal network — Franco has no admin access to it, only consumes it as an API client; no multi-user file-contention concern on the opencode side.
  Model in use: **`Qwen3.6-35B-A3B`** (real, released 2026-04-16, Apache 2.0, sparse MoE — postdates the knowledge cutoff, don't rely on training-data recall). Native context 262,144 tokens, extensible to 1,010,000 via RoPE scaling. Has a "thinking preservation" feature (retains reasoning traces across multi-turn) — worth checking whether `opencode.json`'s model config sets `reasoning`/`interleaved` to use it. Hardware specs of the model server unknown. `$CONFIG_DIR` on the restricted machine is opencode's default (no override).
- **Known model quirk, not an opencode/repo issue**: a "tool call not supported" error was hit on one smaller Qwen model (referred to as "qwen2.7b", exact model unconfirmed). Not fixable from this repo's prompt override; if it recurs, check vLLM's `--tool-call-parser` flag on the model server.
- **The models.dev catalog fetch doesn't block startup on a fully offline machine** — a build-time snapshot is embedded in the offline binary. Only cosmetic fallout is an hourly failed-fetch log line; silence with `OPENCODE_DISABLE_MODELS_FETCH=1`, and add `OPENCODE_MODELS_PATH=<path>` (pointing at `deploy/models-dev-snapshot.json`, see SETUP.md step 3) for fresher data — both vars are needed together. Doesn't matter much either way: this setup's Qwen provider is defined by hand in `opencode.json`, not looked up from the catalog at all.
- Claude's own cross-session memory about this project lives at `~/.claude/projects/<encoded-cwd>/memory/` — the encoded-path segment is machine/account-specific, so don't assume a path recorded here still resolves on whatever machine you're reading this from; check `MEMORY.md` in that directory.
