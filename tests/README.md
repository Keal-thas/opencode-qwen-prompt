# Automated tests

Covers this workspace's feature points with tests that don't require the real vLLM + Qwen model server (none of it is reachable from here anyway - see CLAUDE.md). What's covered, per top-level feature:

- **Qwen prompt override** (`deploy/opencode.json.example` + `deploy/system-prompt.txt`) - `unit/config-consistency.test.mjs` checks the example config is valid JSON wiring `build`/`plan`/`general` to the prompt file, that the prompt file actually differs from the untouched upstream default, and that SETUP.md's inline documentation of the same JSON doesn't drift from the real example file. `integration/docker-prompt-override.test.sh` automates the manual check previously described (but not scripted) in `docker/docker-notes.md`: spins up a throwaway container from the real dev image, wires the override the way SETUP.md instructs, and asserts `opencode debug config` actually resolves `agent.*.prompt` to `system-prompt.txt`'s exact content.
- **`system-prompt-tools.ts` plugin** (dumps the assembled prompt for manual inspection) - `unit/system-prompt-tools.test.mjs` calls its hook directly with fake `experimental.chat.system.transform` input and checks the dump file's header and content, including that each run overwrites rather than appends. Ships as its own committed npm tarball (`plugins/system-prompt-tools/opencode-system-prompt-tools-1.0.0.tgz`), extracted by hand into opencode's own package cache and referenced by a bare name@version exactly like `plugins/hook-logger/`/`plugins/llm-review-gate/` below - see `docs/feature-points/02-system-prompt-tools-plugin.md`.
- **`hook-logger.ts` plugin** (logs every opencode hook event to JSONL) - `unit/hook-logger.test.mjs` calls several of its hooks directly and checks each hook name gets its own append-only `.jsonl` file, and that circular references in hook payloads are serialized instead of throwing.
- **`llm-review-gate.ts` plugin** (LLM safety review gating `bash` calls) - `unit/llm-review-gate.test.mjs` drives it with a fake opencode `client` (no real session, no model): ALLOW/BLOCK verdicts, non-gated tools skipped, the internal review session never reviewing its own calls, and fail-open behavior on a review error or an unparseable verdict.
- **Plugin tarball packaging** (`plugins/system-prompt-tools/`, `plugins/hook-logger/`, `plugins/llm-review-gate/` - each its own committed, pre-packed tarball, installed on the offline target machine by extracting it straight into opencode's own package cache under a bare name@version, no `file:` spec or path, see CLAUDE.md and SETUP.md steps 4/5) - `unit/plugins-tarball.test.mjs` extracts each real committed tarball with `tar` and diffs its file list and byte-for-byte contents against its package's `package.json` `files` list and current source, so an edit to plugin source that forgets to re-run `npm pack` fails the suite instead of silently shipping stale code. The install mechanism itself (does opencode actually skip reinstalling and resolve a pre-seeded, bare-name cache entry with zero network access, with no npm/bun needed on `PATH`) was verified by hand in the `docker/` sandbox with outbound network cut, including a full image rebuild + fresh-container run through the real `docker-entrypoint.sh`-generated config - not covered by this automated test, which only checks tarball-vs-source drift.
- **`toolkits/module-analysis/analyze-modules.mjs`** (batch per-module analysis driver, using `@opencode-ai/sdk` against a real opencode server) - `integration/analyze-modules.test.mjs` runs the real driver against a real opencode server (started by the SDK's `createOpencode()`) with a fake local OpenAI-compatible HTTP server standing in for the model provider, covering the happy path, a failed module leaving no output but a captured log, and the resumability/skip logic for an already-analyzed module (asserted by request count, not just by absence of a log file).
- **Shell scripts generally** (`docker/docker-entrypoint.sh`, `docs/fetch-opencode-docs.sh`) - `unit/shell-syntax.test.mjs` runs `bash -n` over all of them as a cheap regression net.
- **`mcp/oracle/` (oracle MCP server)** - `mcp/oracle/oracle.test.mjs` (not under `tests/unit`, so its `node_modules` resolve correctly - see the file's own header comment) spawns the real `server.js` itself as a child process (matching how a real deployment starts it independently of opencode - see `mcp/oracle/README.md`'s Design section) and drives it over the real Streamable HTTP transport via `@modelcontextprotocol/sdk`'s `Client`: tool listing, a plain `SELECT`, a `CREATE TABLE`/`INSERT`/`SELECT`/`DROP TABLE` round-trip that checks a write actually survives the per-request connection closing (`autoCommit`), a query against a nonexistent table, and a regression test for a connection-failure bug found while first verifying this server by hand. Needs a real Oracle instance - the docker sandbox's `oracle` service, in its own compose project (see `docker/docker-notes.md`), which `docker/dev.sh` always brings up first, so this test can assume it's already there.
- **`mcp/loki/` (loki MCP server)** - `mcp/loki/loki.test.mjs`, same shape as the oracle test (spawns real `server.js`, drives it over real Streamable HTTP). Since its three tools (`loki_query_range`/`loki_labels`/`loki_label_values`) are all read-only, the test seeds its own data by pushing directly to Loki's push API rather than through the MCP server: tool listing, `loki_labels`/`loki_label_values` finding the pushed test stream, `loki_query_range` finding the pushed log line by content, an empty-result query returning cleanly, and malformed LogQL returning a clean error. Needs a real Loki instance - the docker sandbox's `loki` service, in its own compose project (see `docker/docker-notes.md`), which `docker/dev.sh` always brings up first.

Not covered: `docs/fetch-opencode-docs.sh`'s actual GitHub fetch (would hit the network on every test run for no real benefit - it's a docs mirror refresh, not app logic), and anything that requires the real vLLM + Qwen server, which isn't reachable from this machine at all.

## Running the tests

**Development and testing for this repo always happen inside the `docker/` sandbox, never against the host's own node/opencode install** - see CLAUDE.md. The one entry point:

```bash
./tests/run-all.sh
```

This builds the dev image if needed, then runs everything in two stages:

1. `docker/dev.sh run --rm opencode-dev bash tests/run-in-container.sh` - the unit tests (`node --test tests/unit`) and the `analyze-modules.mjs` integration test, all executed *inside* the dev container. Always go through `docker/dev.sh`, not `docker compose` directly - it isolates this worktree's Compose project from any other worktree running the sandbox at the same time (see `docker/docker-notes.md`'s "Per-worktree isolation" section).
2. `tests/integration/docker-prompt-override.test.sh` - the one script that's an exception to "everything runs in the container": it's the thing invoking `docker run` in the first place, so it necessarily runs on the host (same as every `docker compose ...` command already documented in `docker/docker-notes.md`). It touches no host node/opencode install - it starts its own disposable container with a throwaway `HOME`, so a real dev session's own config is never at risk. Everything it actually asserts on (the real `opencode debug config` resolution) still runs inside that container, not on the host.

To run just the container-side suite (e.g. while iterating, without the slower Docker-launching test):

```bash
docker/dev.sh run --rm opencode-dev bash tests/run-in-container.sh
```
