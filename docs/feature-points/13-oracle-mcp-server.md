# oracle mcp server

Lives in `mcp/oracle/`. An MCP server exposing one tool, `oracle_query`, that runs an arbitrary SQL statement against a configured Oracle database — full passthrough by design (no read-only enforcement, no keyword filtering), with an `auditQuery()` extension point left as a no-op for a rule-based or LLM-based check to be added later. One connection opened and closed per request rather than a shared/pooled connection — see `mcp/oracle/README.md` for why. Built directly against `@modelcontextprotocol/sdk` and `oracledb` (thin mode, no Oracle Instant Client needed), same hand-rolled-against-the-raw-API style as `plugins/`.

**Tested:** manually at first, inside the `docker/` sandbox — `npm install` + `node --check` for syntax, then two rounds of a full MCP stdio round-trip (`tools/list` + `tools/call`) against a real `@modelcontextprotocol/sdk` `Client`. First round used a deliberately unreachable Oracle host to exercise the error path, and caught a real bug (a connection failure was crashing out as a raw MCP protocol error instead of the intended `{success: false, error}` tool result — `oracledb.getConnection()` was outside the `try` block), now fixed. Second round ran against a real Oracle instance on the sandbox's docker network: `SELECT`, `CREATE TABLE`, `INSERT`, a fresh request's `SELECT *` confirming the insert persisted (validates `autoCommit: true` across the per-request connection boundary), `DROP TABLE`, and a query against a nonexistent table for the DB-level error path (`ORA-00942`).

Now also automated: `mcp/oracle/oracle.test.mjs` (see `tests/README.md`), covering the same cases above plus a regression test for the connection-failure bug. Wired into `tests/run-in-container.sh`, which runs as part of `./tests/run-all.sh`. **Written but not yet executed** (2026-09-13) — added in a pass that deliberately skipped running Docker to verify it; run `./tests/run-all.sh` to confirm it actually passes before relying on it.

**2026-09-14: converted from a `local`/stdio MCP server to `type: "remote"`/Streamable HTTP.** opencode now connects to this server as an already-running HTTP endpoint (`http://localhost:8090/mcp` by default, configurable via `ORACLE_MCP_PORT`) rather than spawning and owning its process — see `mcp/oracle/README.md`'s Design section for the reasoning (decoupling the server's uptime from opencode's own process lifecycle) and `deploy/opencode.json.example`/SETUP.md step 5 for the updated deployment shape (the server now has to be started independently, e.g. under a process supervisor, before opencode uses it). `oracle.test.mjs` was updated to match: it spawns `server.js` itself as a child process and drives it over the real `StreamableHTTPClientTransport` instead of the `StdioClientTransport` that used to spawn it implicitly. The offline npm-dependency-vendoring gap noted in `mcp/TODO.md` is unaffected by this change — the server still needs to actually run wherever it's deployed, with its dependencies present, regardless of which MCP transport opencode uses to reach it.
