# system-prompt-tools.ts plugin

Source lives in `deploy/system-prompt-tools.ts`. Hooks `experimental.chat.system.transform` to dump the fully-assembled system prompt actually sent to the model (all blocks, including opencode's own `<env>` block) to `~/.local/share/opencode/last-system-prompt.txt` on every request — the only way to confirm the override is really taking effect against the real model, since there's no other visibility into what gets sent. Written in TypeScript against `@opencode-ai/plugin`'s `Plugin` type (the official SDK), matching `plugins/hook-logger.ts`/`plugins/llm-review-gate.ts`.

**Packaging (changed 2026-09-15, install mechanism changed 2026-09-16, simplified 2026-09-17):** copied as a raw `.ts` file into opencode's local-plugin directory (`$CONFIG_DIR/plugins/system-prompt-tools.ts`, SETUP.md step 4) — opencode auto-loads every file in that directory at startup, no package, no registry, no `plugin` config entry at all. `plugins/hook-logger.ts`/`plugins/llm-review-gate.ts` use this same mechanism (SETUP.md step 5), and — unlike the earlier packaged form — each is independently installable since there's no longer a shared package wrapping them. History: shipped as a raw `.ts` file with a hand-derived absolute path wired straight into `plugin` (original), then (2026-09-15) a `file:` npm spec pointing at a versioned tarball, then (2026-09-16) a committed npm tarball extracted by hand into opencode's package cache under a bare `name@version` (working around an assumption that the target machine had no npm registry at all). That assumption turned out to be wrong — the target machine has no *public* internet but does have a working internal npm registry (confirmed 2026-09-17) — which also meant revisiting the whole approach: opencode's own docs (`docs/opencode-docs-reference/plugins.mdx`) describe a `~/.config/opencode/plugins/` local-file auto-load mechanism that was never actually tried here. Confirmed against a real opencode install (not just read from its docs), with outbound network cut, that a `.ts` file dropped there loads and actually executes (a probe plugin's top-level side effect ran) in 0.5s, zero network round-trip, whether or not the file is referenced anywhere in `opencode.json` — see `docker/docker-notes.md`'s "Plugin dependency pre-warming" section. The one real network dependency is opencode's own `@opencode-ai/plugin` support package, installed into `$CONFIG_DIR/node_modules` the first time it ever processes *any* plugin-touching config (local-file or npm-package) — confirmed this is a one-time cost, not per-plugin. Restores the tradeoff the tarball approach had introduced: editing `deploy/system-prompt-tools.ts` takes effect immediately again in the docker sandbox via the live bind mount (docker-entrypoint.sh copies it into `$CONFIG_DIR/plugins/` fresh on every container start), no `npm pack`/rebuild needed.

**Tested:** `tests/unit/system-prompt-tools.test.mjs` — dump content/header format (model/session/block-count), and that each request overwrites rather than appends (the dump always reflects the latest request). No packaging-drift test needed anymore — there's no packaging step to drift from.
