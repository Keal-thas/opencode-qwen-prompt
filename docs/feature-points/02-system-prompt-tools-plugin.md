# system-prompt-tools.ts plugin

Source lives in `deploy/system-prompt-tools.ts`. Hooks `experimental.chat.system.transform` to dump the fully-assembled system prompt actually sent to the model (all blocks, including opencode's own `<env>` block) to `~/.local/share/opencode/last-system-prompt.txt` on every request — the only way to confirm the override is really taking effect against the real model, since there's no other visibility into what gets sent. Written in TypeScript against `@opencode-ai/plugin`'s `Plugin` type (the official SDK), matching `plugins/hook-logger.ts`/`plugins/llm-review-gate.ts`.

**Packaging (changed 2026-09-15, install mechanism changed 2026-09-16):** ships as its own npm package — `deploy/package.json` + the committed, pre-packed `deploy/opencode-system-prompt-tools-1.0.0.tgz` (regenerate with `npm pack` in `deploy/` after editing the source; `tests/unit/plugins-tarball.test.mjs` fails the build if it drifts) — installed on the target machine by extracting that tarball by hand straight into opencode's own package cache (`$CACHE_DIR/packages/opencode-system-prompt-tools@1.0.0/`, SETUP.md step 4) and referencing it in `opencode.json`'s `plugin` array as the bare `"opencode-system-prompt-tools@1.0.0"` — no path, no `file:` spec. `plugins/opencode-hook-plugins-1.0.0.tgz` uses this same mechanism for `hook-logger.ts`/`llm-review-gate.ts` (SETUP.md step 5). Previously this shipped as a raw `.ts` file with a hand-derived absolute path wired straight into `plugin`, then (2026-09-15) switched to a `file:` npm spec pointing at a versioned tarball; switched again (2026-09-16) to this cache-preseed form once testing showed opencode resolves a `plugin` entry by extracting it into `~/.cache/opencode/packages/<the literal spec string>/` and skips reinstalling if that directory already exists — so pre-seeding it under a bare `name@version` key gets a config with zero hardcoded paths, still fully offline. Confirmed against a real opencode install (not just read from its docs), with outbound network cut, that this resolves instantly with no network round-trip and no npm/bun needed on `PATH` — see `docker/docker-notes.md`'s "Plugin dependency pre-warming" section for how that was verified. This rests on opencode's own undocumented cache-key behavior, not a contract its docs promise — re-verify after bumping the pinned opencode version. Tradeoff: unlike `deploy/system-prompt.txt`, editing `deploy/system-prompt-tools.ts` no longer takes effect immediately in the docker sandbox via the live bind mount — it needs `npm pack` plus an image rebuild first, same as `plugins/`'s packages already required.

**Tested:** `tests/unit/system-prompt-tools.test.mjs` — dump content/header format (model/session/block-count), and that each request overwrites rather than appends (the dump always reflects the latest request). Its shipped packaging is covered by `tests/unit/plugins-tarball.test.mjs`, same as `plugins/`'s tarball.
