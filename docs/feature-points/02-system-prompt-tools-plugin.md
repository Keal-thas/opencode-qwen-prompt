# system-prompt-tools.ts plugin

Source lives in `plugins/system-prompt-tools/system-prompt-tools.ts`. Hooks `experimental.chat.system.transform` to dump the fully-assembled system prompt actually sent to the model (all blocks, including opencode's own `<env>` block) to `~/.local/share/opencode/last-system-prompt.txt` on every request — the only way to confirm the override is really taking effect against the real model, since there's no other visibility into what gets sent. Written in TypeScript against `@opencode-ai/plugin`'s `Plugin` type (the official SDK), matching `plugins/hook-logger/hook-logger.ts`/`plugins/llm-review-gate/llm-review-gate.ts`.

**Packaging (changed 2026-09-15, install mechanism changed 2026-09-16 then again 2026-09-17):** ships as its own npm package — `plugins/system-prompt-tools/package.json` + the committed, pre-packed `opencode-system-prompt-tools-1.0.0.tgz` (regenerate with `npm pack` in that directory after editing the source; `tests/unit/plugins-tarball.test.mjs` fails the build if it drifts) — installed on the target machine by extracting that tarball by hand straight into opencode's own package cache (`$CACHE_DIR/packages/opencode-system-prompt-tools@1.0.0/`, SETUP.md step 4) and referencing it in `opencode.json`'s `plugin` array as the bare `"opencode-system-prompt-tools@1.0.0"` — no path, no `file:` spec. `plugins/hook-logger/` and `plugins/llm-review-gate/` each use this same mechanism as their own independent packages (SETUP.md step 5) — unlike the original bundled form, installing one doesn't require the other. History: shipped as a raw `.ts` file with a hand-derived absolute path wired straight into `plugin`, then (2026-09-15) a `file:` npm spec pointing at a versioned tarball, then (2026-09-16) this cache-preseed form once testing showed opencode resolves a `plugin` entry by extracting it into `~/.cache/opencode/packages/<the literal spec string>/` and skips reinstalling if that directory already exists. Briefly (2026-09-17) replaced with opencode's documented local-plugin-directory mechanism (`~/.config/opencode/plugins/*.ts`, zero packaging) after confirming the target machine's "no internet" only ever meant no public internet — but that mechanism gives every local plugin one shared dependency tree via a single `$CONFIG_DIR/package.json`, with no per-plugin version isolation, so it was reverted back to this per-plugin tarball form the same day (Franco's call) once that tradeoff was weighed against the (acceptable) risk of resting on an undocumented cache-key contract. Confirmed against a real opencode install (not just read from its docs), with outbound network cut, that this resolves instantly with no network round-trip and no npm/bun needed on `PATH` — see `docker/docker-notes.md`'s "Plugin dependency pre-warming" section for how that was verified. This rests on opencode's own undocumented cache-key behavior, not a contract its docs promise — re-verify after bumping the pinned opencode version. Tradeoff: unlike `deploy/system-prompt.txt`, editing `plugins/system-prompt-tools/system-prompt-tools.ts` no longer takes effect immediately in the docker sandbox via the live bind mount — it needs `npm pack` plus an image rebuild first, same as `plugins/hook-logger/`/`plugins/llm-review-gate/` already require.

**Tested:** `tests/unit/system-prompt-tools.test.mjs` — dump content/header format (model/session/block-count), and that each request overwrites rather than appends (the dump always reflects the latest request). Its shipped packaging is covered by `tests/unit/plugins-tarball.test.mjs`.
